# 지난 뉴스레터 기사 재선정 방지 명세 (feat/history-dedup)

## 1. Original Requirements

> 지난 뉴스레터와 겹치는 뉴스 없이 뉴스를 업로드 하고 싶어

(`/sdd:spec` 사용자 입력, 2026-11-04)

이전 요청:

> 웹 페이지에 정리해 둔 뉴스레터에서 날짜가 다른데도 서로 중복되는 뉴스가 가끔 올라오는데
> 이를 해결할 방안은 없을까 매일 새로운 뉴스를 받고싶어

원인 분석 뒤 정리한 요구사항(첫 `/sdd:spec` 인자, 2026-11-04):

> 지난 뉴스레터에 이미 실린 기사가 다른 날짜 뉴스레터에 다시 나오지 않게 한다. 원인: 수집 구간이 실행 시각 기준 최근 24시간(windowHours)이라 실행 간격이 24시간보다 짧으면(예: 2026-11-03 23:41 생성 → 2026-11-04 00:23 생성, 42분 간격으로 25개 사안이 사실상 동일; 2026-10-31 19:35 → 2026-11-01 12:00, 16.5시간 간격으로 URL 7건 중복) 같은 기사가 다시 선정된다. 정상 12시 실행끼리는 중복 0건. 해결: 실행 시 news/의 최근 N일(설정 historyDays, 기본 7, 0이면 끔) Markdown을 MarkdownNewsletterReader로 읽어 원문 URL과 같은 사안 URL을 모으고, 이 URL과 같은 기사를 정제 단계에서 후보에서 뺀다. 출력 날짜와 같은 날짜 파일(같은 날 재실행)과 그 이후 날짜 파일은 제외한다. 읽을 수 없는 Markdown은 경고 로그 후 건너뛴다. 제목 유사도로 이어지는 사안까지 막는 것은 범위 밖. 기존 명세는 docs/feature/daily-news/spec.md(FR-3 정제 및 중복 제거)를 참고.

## 2. Overview

지금 파이프라인은 **실행 시각 기준 최근 24시간** 안에 발행된 기사만 후보로 쓴다(기존 FR-2.3, `sources.yml`의 `windowHours: 24`). 지난 뉴스레터에 무엇이 실렸는지는 보지 않는다. 그래서 두 실행의 간격이 24시간보다 짧으면 수집 구간이 겹치고, 같은 기사가 다음 날짜 뉴스레터에 다시 뽑힌다.

`news/`의 7개 파일(2026-10-29 ~ 2026-11-04)을 비교한 결과는 다음과 같다. 날짜마다 원문 URL과 같은 사안 URL을 모아 날짜 사이에서 겹치는 URL을 셌다.

| 날짜 쌍 | 생성 시각 | 간격 | 겹친 기사 URL |
|---|---|---|---|
| 2026-10-31 → 2026-11-01 | 19:35 → 12:00 | 16.5시간 | 7건 |
| 2026-11-03 → 2026-11-04 | 23:41 → 00:23 | 42분 | 53건 중 53건 — 25개 사안 제목까지 모두 같음 |
| 나머지 이웃한 날짜 | 12~14시 | 약 23~25시간 | 0건 |

간격이 짧아지는 이유는 수동 재실행, 오늘 파일 재생성, 백업 예약 실행 등이다. 이번 작업은 실행 시각과 상관없이 **이전 날짜 뉴스레터에 이미 실린 기사를 후보에서 뺀다**. 수집 구간(24시간), 사안 묶기·점수·요약 방식, Markdown·웹 출력 형식은 바꾸지 않는다.

## 3. Goals

- G1. 출력 날짜 이전 `historyDays`일 안의 뉴스레터에 실린 기사(원문 URL, 같은 사안 URL)는 새 뉴스레터에 다시 나오지 않는다.
- G2. 실행 간격이 24시간보다 짧아도(같은 밤 연속 실행 포함) G1이 지켜진다.
- G3. 같은 날짜를 다시 실행하면 지금처럼 그날 파일을 덮어쓴다(기존 FR-7.4). 그날 파일에 실린 기사는 빼지 않는다.
- G4. 정상 12시 실행 결과는 지금과 같다. 지금도 겹치는 URL이 0건이므로 빼는 기사가 없다.
- G5. 기능은 설정 하나로 끌 수 있고, 지난 Markdown이 없거나 깨져 있어도 뉴스레터 생성은 실패하지 않는다.

## 4. User Stories

- US1. 구독자로서 매일 뉴스레터를 열었을 때 전날 본 기사가 아니라 **새 기사**만 보고 싶다.
- US2. 운영자로서 실행이 늦어지거나 같은 날 여러 번 수동 실행해도, 다음 날 뉴스레터가 전날과 겹치지 않기를 바란다.
- US3. 운영자로서 오늘 뉴스레터를 다시 만들면(같은 날 재실행) 오늘 고른 기사가 스스로 빠지지 않고 지금처럼 덮어쓰여야 한다.
- US4. 운영자로서 몇 일 치를 비교할지 `sources.yml`에서 바꾸거나 기능을 끌 수 있어야 한다.
- US5. 운영자로서 실행 로그에서 지난 뉴스레터 때문에 몇 건이 빠졌는지 확인하고 싶다.

## 5. Functional Requirements

### FR-1 지난 뉴스레터 기사 목록 만들기
- FR-1.1 실행할 때 출력 루트의 `news/YYYY/MM/YYYY-MM-DD.md` 중 날짜가 **[출력 날짜 − `historyDays`일, 출력 날짜 − 1일]** 범위인 파일을 읽는다. 예: 출력 날짜 2026-11-04, `historyDays: 7` → 2026-10-28 ~ 2026-11-03.
- FR-1.2 출력 날짜와 같은 날짜 파일(같은 날 재실행)과 출력 날짜보다 뒤 날짜 파일(`--date`로 과거 날짜를 다시 만들 때)은 읽지 않는다.
- FR-1.3 각 파일은 기존 `MarkdownNewsletterReader`로 읽고, 모든 카테고리 기사의 **원문 URL**과 **같은 사안 URL**을 모아 하나의 집합으로 만든다.
- FR-1.4 형식이 맞지 않거나 읽을 수 없는 파일은 파일 경로와 이유를 경고 로그로 남기고 건너뛴다. 나머지 파일은 그대로 쓴다.
- FR-1.5 `news/` 폴더나 해당 날짜 파일이 없으면 빈 집합으로 처리한다(첫 실행, 새 루트).
- FR-1.6 파일을 쓰지 않는 `--dry-run`에서도 지난 파일을 읽어 똑같이 적용한다(읽기만 한다).

### FR-2 후보에서 빼기 (기존 FR-3 정제 단계에 추가)
- FR-2.1 정제 단계에서 URL을 정규화한 뒤(기존 FR-3.1) 정규화한 URL이 FR-1 집합에 있는 기사는 후보에서 뺀다. 카테고리와 상관없이 뺀다.
- FR-2.2 비교는 정규화한 URL 문자열이 완전히 같을 때만 한다. 제목이 비슷한 기사(같은 사안의 새 기사)는 빼지 않는다(범위 밖, §7 C3).
- FR-2.3 뺀 뒤의 기사로 사안 묶기·선정·요약을 지금과 같이 한다. 후보가 카테고리당 5개보다 적으면 있는 만큼만 표시한다(기존 FR-4.4).
- FR-2.4 오늘의 키워드(기존 FR-6.1)와 헤더의 "중복 제거 N건"은 뺀 뒤의 기사 기준이다. 전날 기사 제목이 오늘 키워드를 정하지 않게 하기 위해서다.

### FR-3 설정
- FR-3.1 `sources.yml`에 `historyDays`(0 이상 정수)를 둔다. 기본 설정 파일 값은 `7`이다.
- FR-3.2 `historyDays: 0`이면 지난 파일을 읽지 않고 아무 기사도 빼지 않는다(지금 동작과 같음).
- FR-3.3 `historyDays`를 생략하면 `7`로 본다(`--config`로 쓰는 옛 설정 파일 호환). 음수나 정수가 아닌 값은 설정 오류(종료 코드 1)다.

### FR-4 로그
- FR-4.1 읽은 파일 수, 건너뛴 파일 수, 모은 URL 수를 로그로 남긴다.
- FR-4.2 정제 로그에 지난 뉴스레터 때문에 뺀 기사 수를 기존 항목(허용되지 않는 링크, 기간 밖, 중복)과 따로 남긴다.

### FR-5 바꾸지 않는 것
- FR-5.1 Markdown·웹 페이지·README 출력 형식은 바꾸지 않는다. 옛 파일도 그대로 읽힌다.
- FR-5.2 수집 구간(`windowHours`), 사안 묶기·점수·대표 기사 규칙, 요약 방식은 바꾸지 않는다.
- FR-5.3 Markdown 보관 정책(기존 FR-7.5, 무기한)은 바꾸지 않는다. `newsDays`를 `historyDays`보다 짧게 두면 남아 있는 파일만 비교한다.

## 6. Non-Functional Requirements

- NFR-1 성능: 지난 파일 읽기는 네트워크를 쓰지 않고, `historyDays: 7`(파일 7개, 각 약 15KB)에서 1초 안에 끝난다. 전체 실행 시간 기준(5분)은 그대로다.
- NFR-2 신뢰성: 지난 파일 문제(없음, 깨짐, 인코딩)로 뉴스레터 생성이 실패하지 않는다(FR-1.4, FR-1.5). CRLF 줄바꿈 파일도 읽는다(기존 리더가 지원).
- NFR-3 유지보수성: 지난 기사 목록을 만드는 부분은 파일 시스템 경로와 날짜를 받는 별도 클래스로 두고, 정제기(`ArticleCleaner`)는 URL 집합만 받는다. 네트워크 없이 임시 폴더 fixture로 단위·통합 테스트할 수 있다.
- NFR-4 관찰성: FR-4의 로그로 실행마다 몇 건이 왜 빠졌는지 알 수 있다.
- NFR-5 보안·비용: 새 의존성, 비밀값, 외부 요청을 추가하지 않는다.

## 7. Constraints & Assumptions

### Constraints
- C1. 언어와 구조는 기존 그대로다(Java 21, Gradle, `dailynews` 패키지).
- C2. 지난 기사 목록의 출처는 저장소의 `news/` Markdown뿐이다. 별도 상태 파일이나 DB를 추가하지 않는다. GitHub Actions는 매 실행 `main`을 체크아웃하므로 지난 Markdown이 항상 있다.
- C3. 범위 밖: 제목 유사도로 "어제와 이어지는 사안"을 막는 것, 웹 페이지에 이미 게시된 옛 날짜 뉴스레터를 고치는 것(2026-11-01, 2026-11-04 등의 기존 중복은 그대로 둔다), 실행 예약 방식 변경.

### Assumptions
- A1. Markdown의 원문 URL과 같은 사안 URL은 정제 단계에서 정규화한 URL을 그대로 쓴 값이다(`MarkdownRenderer` 출력). 따라서 문자열 비교로 같은 기사를 찾을 수 있다. 같은 사안 링크의 `(`, `)` 이스케이프는 `MarkdownNewsletterReader`가 되돌린다.
- A2. 언론사는 같은 기사의 URL을 바꾸지 않는다. 기사 수정으로 URL이 바뀌면 다른 기사로 본다.
- A3. 7일이면 충분하다. RSS 피드에 남는 기사는 보통 하루~이틀 치이고, 24시간 수집 구간을 쓰므로 그보다 오래된 기사는 원래 후보가 되지 않는다.

## 8. Success Criteria

- SC1. (단위) 출력 날짜 2026-11-04, `historyDays: 7`에서 2026-10-28 ~ 2026-11-03 파일만 읽고, 2026-10-27·2026-11-04·2026-11-05 파일은 읽지 않는다.
- SC2. (단위) 원문 URL과 같은 사안 URL이 모두 집합에 들어간다. 깨진 파일 1개가 섞여 있으면 경고 로그를 남기고 나머지 파일의 URL은 모두 모은다. `news/`가 없으면 빈 집합이다.
- SC3. (단위) 정제기는 집합에 있는 URL의 기사를 카테고리와 상관없이 빼고, 뺀 건수를 따로 센다. 집합이 비어 있으면 결과가 지금과 같다.
- SC4. (통합, fixture) 전날 Markdown에 fixture 기사 URL 일부를 넣고 파이프라인을 실행하면, 새 뉴스레터의 원문·같은 사안 URL 중 전날 URL은 0건이다. 같은 날짜 파일이 이미 있어도 그 파일의 기사는 빠지지 않는다(재실행 결과가 지금과 같다).
- SC5. (설정) `historyDays` 생략 → 7, `0` → 기능 꺼짐, `-1`·`"a"` → 설정 오류.
- SC6. (재현) 2026-11-03 Markdown(23:41 생성)이 있는 상태에서 실제 피드로 2026-11-04를 `--dry-run` 실행하면, 선정 기사 URL 중 2026-10-28 ~ 2026-11-03 뉴스레터와 겹치는 것이 0건이다.
- SC7. (회귀) 기존 테스트(`./gradlew test`)가 모두 통과하고, 골든 Markdown 출력은 바뀌지 않는다.
